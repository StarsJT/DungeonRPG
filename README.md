# DungeonRPG —— 随机地牢探险 RPG

> 数据结构与算法 · 综合类实验项目
> 武汉理工大学 机电工程学院 · 智能制造 2301 · 2026 年秋季

## 一句话概述

表面是一个可玩的回合制 Roguelike 小游戏，内核是把《数据结构与算法》教材的核心章节
**系统化串联应用**，并产出一份可复现的算法性能对比实验报告。

## 课程对应

| 游戏功能 | 数据结构 / 算法 | 教材章节 |
|---|---|---|
| 地图瓦片存储 | 一维数组模拟二维、连续内存布局 | 线性表 / 数组 |
| 随机地牢生成 | BSP 二叉树递归切分、房间连通图、并查集校验 | 树、图、递归与分治 |
| 怪物追击寻路 | A\* / BFS / Dijkstra、小顶堆 open 表、cameFrom 栈式还原路径 | 图、栈、排序 |
| 视野与迷雾 | 递归阴影投射（8 个八分仪）、递归转迭代显式栈 | 栈、递归 |
| 回合调度 | 优先队列 / 二叉堆，seq 做稳定 tie-break | 树、排序 |
| 背包系统 | 多关键字排序、堆取最大、Top-K 选装备 | 排序、查找 |
| 物品与怪物数据 | 哈希表 ID→模板 O(1) 查找、字符串搜索 | 查找、串 |
| 消息日志 | 环形队列（固定容量 FIFO） | 队列 |
| 存档 / 读档 | 二进制序列化、版本号 + 校验和 | 文件、综合 |
| 性能对比面板 | 计数器 + 高精度计时，复杂度实测 | 算法分析 |

## 三层架构

```
ui/    渲染 · 输入 · HUD · DebugOverlay   → 依赖 core，只读 GameSnapshot，禁止反向写
io/    CSV 读表 · 存档读写                → 依赖 core
core/  地图 · 生成 · 寻路 · 视野 · 战斗    → 纯 C++17，零外部依赖，不含任何绘图代码
```

core 不含绘图代码这条铁律带来三个好处：
1. 六人可真正并行，算法不必等界面；
2. core 可脱离窗口做单元测试；
3. 前端从 Qt 换成 EasyX 只改 `ui/`。

## 构建与运行

```bash
# ★ 本机必须显式指定 MinGW 生成器：默认探测到的 MSVC 无法通过编译器测试
cmake -S . -B build -G "MinGW Makefiles"
cmake --build build
ctest --test-dir build          # 单元测试
./build/bin/dungeon_console     # 控制台版（可加种子参数：dungeon_console 12345）
```

### 已产出的实验数据（★ 报告第 4 章，均由程序实测生成）

**生成算法正确性**：1000 个随机种子 → 并查集连通性校验 100% 通过；
100 张图合计 `Door=1009  Rubble=2647  Lava=671`（带权地形覆盖率达标）。

**三算法对比（合成对照图，21×11 带熔岩墙）**

| 算法 | 步数 | 总代价 | 扩展节点 |
|---|---|---|---|
| BFS | 20 | 3910 | 226 |
| Dijkstra | 20 | 2164 | 215 |
| A\* | 20 | 2164 | **67** |

**三算法对比（真实地牢 80×45，30 组起终点 × 20 次重复取平均）**

| 算法 | 平均扩展节点 | 平均耗时(ms) |
|---|---|---|
| BFS | 417.6 | **0.020** |
| Dijkstra | 418.4 | 0.038 |
| A\* | **256.6** | 0.028 |

> 结论（答辩口径）：A\* 与 Dijkstra 的**路径总代价完全相同**（都最优），
> 但 A\* 靠启发式剪枝少扩展约 39% 的结点；BFS 单次开销最低却完全不考虑地形代价，
> 在带权地图上代价最高。原始 CSV 见 `docs/实验数据/`。

**递归 FOV vs 迭代 FOV（累计计时 50000 次取平均，空旷场地）**

| 视野半径 | 可见格数 | 递归(ms) | 迭代(ms) |
|---|---|---|---|
| 4 | 49 | 0.00050 | 0.00072 |
| 8 | 197 | 0.00141 | 0.00160 |
| 16 | 797 | 0.00473 | 0.00470 |

> 半径翻倍 → 可见格数约 ×4（**O(r²) 的实测证据**）。
> 但在有遮挡的真实地牢里**迭代版反而慢 1.5~2 倍** —— 递归转迭代的价值是
> 避免栈溢出与内存可控，**不是性能优化**。原始 CSV：`docs/实验数据/bench_fov.csv`

**哈希 vs 线性查找（20 万次查询累计计时取平均）**

| 数据量 | 哈希(us) | 线性(us) | 倍数 |
|---|---|---|---|
| 100 | 0.0050 | 0.0557 | 11× |
| 1000 | 0.0050 | 0.1302 | 26× |
| 10000 | 0.0050 | 1.3970 | 279× |

> 哈希已低于测量精度（1 ms ÷ 20 万次 = 5 ns），应读作"**< 0.005 us**"的上界。

**BF vs KMP 子串检索（全表扫描一次，us）**

| 数据量 | 短模式串 BF | 短模式串 KMP | 长模式串 BF | 长模式串 KMP |
|---|---|---|---|---|
| 100 | 1.2071 | **0.6006** | 0.5395 | **0.4006** |
| 1000 | 10.0124 | **6.2720** | **3.0000** | 5.2642 |
| 10000 | 101.5838 | **63.3832** | **40.0838** | 51.8241 |

> ★ KMP 只在"短模式串 + 命中多"时领先；"长模式串 + 命中少"时 BF 反超 ——
> 因为命中少时 BF 常在首字符就失配。原始 CSV：`docs/实验数据/bench_lookup.csv`

### 第四组实验：连通性判定 并查集 vs BFS

**静态场景**（一次性全图连通分量计数）：200×200 → BFS 0.97 ms / 并查集 0.51 ms —— 同量级。
**动态场景**（边逐批到达 + 每批 100 次连通性查询）：并查集 0.57 ms vs BFS **731 ms —— 1294 倍**。

> ★ 结论：**算法选择取决于查询模式**。一次性标记用 BFS；在线反复查询用并查集。
> 这也是怪物结盟选并查集的理由。原始 CSV：`docs/实验数据/bench_uf.csv`

### 时间回溯与怪物结盟（M6 创新点）

- **时间回溯**（`R` 键，控制台/窗口版通用）：每次行动前把整局状态序列化压栈，
  上限 30 步。复用存档的序列化规则 —— **"存档"和"快照"本质是同一件事**。
  消耗品喝了、血被打掉了、甚至**下楼之后**，回溯都能回去（地图由 seed+depth 重建）。
- **并查集怪物结盟**：同连通区域的怪属一个巢穴，一只发现玩家 → 整组一起追
  （警觉共享），传播 O(α)。快照里被联动激怒的怪染红显示。
- **算法竞速场**：调试面板同屏显示三算法在同一起终点上的扩展节点/耗时，
  `fig_race` 把三张扩散图拼成一张三面板图 —— 实测同一条路 A\* 少扩展 57%。
- **LRU 记忆迷雾**：地形轮廓永久记忆（explored），细节（掉落物）只记最近
  384 格（`list` + `unordered_map` 的标准 LRU，淘汰跳过视野内格子）。
  走远了的地方只剩剪影 —— 你忘了那里有什么。
- **怪物表数据驱动**：15 种怪物全部来自 `data/monsters.csv`，脏行逐条跳过，
  文件缺失回落内置表 —— 与物品表同一条降级原则。
- **地面掉落物持久化**：存档 v2。地图可由 `(seed, depth)` 重建，但
  "哪几个宝箱已被摸过"不可重建 —— 不存它就会在读档/回溯后复活（已修，见缺陷 #30）。
- **配置表热重载**（`T` 键）：改 CSV 不用重开游戏；失败不动旧表；
  只影响之后生成的东西（已在场的怪与地上的物品保持原样）。
- **遗忘的渐进淡出**（窗口版）：被 LRU 挤出的格子 0.8 秒从"记得"褪成"剪影"，
  重新看见时 0.25 秒亮回来。动画状态留在表现层，不进 core 与存档。

## 关键设计决策

1. **为什么要带权地形？** 若格子只有可走/不可走，Dijkstra 会退化成 BFS，
   三算法对比曲线完全重合，报告实验章节失效。故给门/碎石/熔岩不同通行代价。
2. **为什么 A\* 用 octile 而不是曼哈顿距离？** 八方向移动下曼哈顿距离会高估真实代价，
   破坏启发式的可采纳性，A\* 不再保证最优解。
3. **`std::priority_queue` 没有 decrease-key 怎么办？** 采用 lazy deletion：
   重复入堆 + closed 标记 + 出堆时跳过已处理节点。
4. **为什么 Rng 自己实现？** xorshift32 只有 4 字节状态，存档存一个 `uint32`
   就能 100% 还原整张地图；`std::mt19937` 状态 2.5KB 且跨平台序列不一致。
